## 1. Problem Understanding

System purpose:
The system manages registration for a single event with a fixed capacity. It allows users to register, places extra users on a FIFO waitlist when the event is full, and updates the registration state after each operation.

Inputs to the system:
- event capacity
- user ID
- registration request
- cancellation request
- status query

Outputs produced by the system:
- registration result for a user
- waitlist result for a user
- current user status
- updated ordered list of registered users
- updated ordered list of waitlisted users

Primary goal of the system:
The primary goal of the system is to manage event registration automatically and predictably with minimal manual effort, while remaining clear, deterministic, and reliable for different user needs.

---

## 2. Assumptions

A1:
The system manages exactly one event at a time.

A2:
Each user is identified by a unique user ID.

A3:
Requests are processed one at a time in a deterministic order.

A4:
Capacity is a non-negative integer.

A5:
A user may exist in only one state at a time: registered, waitlisted, or absent.

A6:
The system must preserve FIFO ordering for the waitlist.

A7:
Users may cancel whether they are registered or waitlisted.

A8:
The system should return concise results, but important automatic changes must still be explicit.

---

## 3. Functional Requirements

FR1:
The system shall accept a fixed capacity for a single event.

FR2:
The system shall allow a user to register for the event.

FR3:
The system shall register users until capacity is reached.

FR4:
The system shall place additional users in a FIFO waitlist when the event is full.

FR5:
The system shall automatically promote the earliest waitlisted user when a registered user cancels.  [persona-derived]

FR6:
The system shall prevent duplicate registration requests from users who are already registered or waitlisted.

FR7:
The system shall allow a user to cancel their registration or waitlist participation.

FR8:
The system shall allow a user to query their current status.

FR9:
The system shall return an explicit outcome for each request, such as registered, waitlisted, canceled, rejected, or not found.  [persona-derived]

FR10:
The system shall provide a clear explanation when a request is rejected, when a user is waitlisted, or when a waitlisted user is promoted.  [persona-derived]

FR11:
The system shall produce deterministic outcomes when the same sequence of operations is repeated from the same initial state.  [persona-derived]

FR12:
The system shall return concise status information with minimal extra interaction.  [persona-derived]

## 5. Acceptance Criteria

AC1:
Given an event with capacity 2 and 2 users already registered,
When a third user submits a registration request,
Then the system places that user on the waitlist instead of the registered list.

AC2:
Given an event with capacity 2, users A and B registered, and users C then D on the waitlist,
When user A cancels,
Then user C is promoted to the registered list before user D.

AC3:
Given a user is already registered or already on the waitlist,
When that same user submits another registration request,
Then the system rejects the duplicate request and returns an explicit outcome.

AC4:
Given a user is neither registered nor waitlisted,
When that user submits a cancellation request,
Then the system returns an explicit not-found or failure outcome.

AC5:
Given the same initial state and the same sequence of registration and cancellation operations,
When the system executes that sequence twice,
Then the final registered list and waitlist order are identical in both runs.

AC6:
Given a user requests their status,
When the system processes the status query,
Then it returns exactly one valid state indicating whether the user is registered, waitlisted, or absent.

AC7:
Given the event capacity is 0,
When a user submits a registration request,
Then the system does not register the user and handles the case explicitly according to system rules.

AC8:
Given a waitlisted user is promoted after a cancellation creates an open spot,
When the promotion occurs,
Then the system updates the registration state so the promoted user appears in the registered list and no longer appears in the waitlist.

AC9:
Given a registration request is rejected, a user is placed on the waitlist, or a waitlisted user is promoted,
When the system returns the result of that operation,
Then it includes a clear explanation of what happened and why.

## 6. Edge Cases

EC1:
Expected system behavior:
If capacity = 0, no user is ever registered and all registration attempts are handled explicitly according to system rules.  [persona-derived]

EC2:
Expected system behavior:
If a user who is already registered or already waitlisted tries to register again, the system rejects the duplicate request with an explicit result.  [persona-derived]

EC3:
Expected system behavior:
If a user who is not in the system tries to cancel, the system returns an explicit failure or not-found result instead of failing silently.  [persona-derived]

EC4:
Expected system behavior:
If multiple users are on the waitlist and one registered user cancels, only the earliest waitlisted user is promoted.

EC5:
Expected system behavior:
If the same sequence of operations is repeated from the same initial state, the resulting registered list and waitlist must be identical.

EC6:
Expected system behavior:
If a user cancels and then re-registers later, the new request is processed against the updated system state.

EC7:
Expected system behavior:
If a waitlisted user cancels before promotion, they are removed and the remaining waitlist positions update correctly.
